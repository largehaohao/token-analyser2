# Coding Agent 成本分析器：需求访谈

状态：四轮 Q1–Q20 已全部由用户采用默认建议，产品决策已收敛。本地 MVP 已按[规格](mvp-spec.md)实现；日志兼容与性能等仍须用脱敏样本实测，验证记录见 `.scratch/coding-agent-cost-monitor/README.md`。

## 用户提出的目标

帮助用户理解 Coding Agent 的 Token / credits 消耗去向，并通过直观 dashboard 实时观察运行中会话、复盘已结束的任务、发现可疑开销、理解原因和获得优化建议。

候选 MVP 能力：Codex / Claude Code session 导入、每轮用量与费用、子 Agent 消耗、重复读取检测、wait/poll 检测、compaction loop 检测、浪费金额与优化建议。

上述能力的产品范围与统计原则已经过四轮访谈确认；数据可得性与来源版本兼容仍按样本验证结果如实声明。

## 问题证据与边界

已核对以下原始 Issue，三者均发表于 2026-07-24。核验确认的是作者作出了这些报告，不代表维护者已经复现、官方账本已经对账，或这些结果对所有任务成立。

- [Issue #35259](https://github.com/openai/codex/issues/35259)：19.8% 对应一个从周额度重置到首次观察到已使用 49% 的多会话统计窗口，不是单个长任务。作者排除了子会话复制的历史前缀与未变化的累计用量快照；等待 / 状态查询轮次占该窗口原始 Token 的 19.8%。作者明确声明 credits 是公开价目表估算，不是实际订阅账本。
- [Issue #35177](https://github.com/openai/codex/issues/35177)：固定合成仓库、每组两次只读实验；无批处理指导的两次运行分别报告 23 / 25 个 sessions、7.5M / 17.6M 原始 tokens，以及按公开价目表折算的 267 / 605 credits。不能将这些数字说成已经核实的实际扣款。
- [Issue #35226](https://github.com/openai/codex/issues/35226)：作者报告上下文压缩后反复读取文件、技能和记忆，并持续消耗额度。属于问题自述，不能据此认定所有压缩后的重读都是浪费。

原始 Token 占比、按价目表估算的费用占比、实际计费占比和可以避免的费用不是同一个统计量。后续解析还必须处理复制历史与累计快照，否则分析器自身会夸大消耗。

### F2：日志可观测性的事实前置

公开资料核验所得，不代表已经用本项目解析器验证过任何实际日志版本：

- [Codex 协议源码](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs)包含单次 / 累计用量及父子来源相关字段，但字段存在不保证每一行都是新的独立模型调用。具体版本的历史复制与去重边界仍需样本验证。
- [Claude SDK 计量说明](https://code.claude.com/docs/en/agent-sdk/cost-tracking)提示 assistant 消息的输出用量可能只是占位值，最终结果和流式更新具有不同口径；消息 ID 重复和累计成本也不能简单逐条相加。SDK 文档的保证不能无条件推广到所有原生历史 JSONL。
- [Claude 子代理说明](https://code.claude.com/docs/en/sub-agents#resume-subagents)与[会话说明](https://code.claude.com/docs/en/agent-sdk/sessions#fork-to-explore-alternatives)提供子日志位置与 fork 行为线索；旧版本、缺失文件或复制历史仍需显式处理。
- 日志中的 credits 余额快照、按费率计算的成本和实际逐请求扣款是不同信息。来源没有完整账本或工具级计量时，不能宣称知道某次读取的确切费用。

这些限制引出 Q7；它们不构成承诺所有 Codex / Claude Code 版本都能完整导入。

### F3：实时采集的事实前置

- [MDN：getFile](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/getFile)说明文件变化后需要重新取得 File；一次选择或拖入的普通文件对象不会自动持续反映日志增长。
- 浏览器可以通过获授权的文件句柄重新读取，但[目录选择](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)受浏览器支持、安全上下文和用户操作要求限制；[保存句柄也不等于永久授权](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemHandle/queryPermission)。
- 工程推断：本地只读采集进程可增量读取日志并向本机 dashboard 推送数据，但增加启动进程的步骤。[Node 文件监听文档](https://nodejs.org/api/fs.html#caveats)提示平台差异和文件删除重建等边界；仅监听一次文件不足以保证持续采集可靠。
- 两种采集方式都只能展示来源已记录的信息。页面刷新频率与模型用量上报频率是两回事；尚未产生的 usage 不能凭经过时间伪造。

事实核验没有读取用户私人会话，也没有运行采集实现。用户在第三轮 Q9 依据这些边界选择了本地只读采集服务与浏览器 dashboard。

### F4：异常检测的可观测边界

- [Codex 持久化策略](https://github.com/openai/codex/blob/6c59264b14b963d45d1005e7a8b1de87d4b054e2/codex-rs/rollout/src/policy.rs)和[调用结构](https://github.com/openai/codex/blob/6c59264b14b963d45d1005e7a8b1de87d4b054e2/codex-rs/protocol/src/models.rs)显示：工具调用与返回、用户消息、压缩相关记录通常可观察，但部分执行 / 协作状态事件不持久化；协议有字段不代表原生 JSONL 必然有该记录。
- [Claude 会话文档](https://code.claude.com/docs/en/agent-sdk/sessions)与[子代理压缩说明](https://code.claude.com/docs/en/sub-agents#auto-compaction)提供工具活动、用户消息和压缩边界的线索。具体记录完整性仍以验证过的版本和实际样本为准。
- 工程推断：同路径不保证同内容；内容截断、读取范围不同、缺文件版本时不能断言重复读取相同信息。没有观察到写工具也不能证明文件未变化，shell、其他 Agent 或外部进程都可能写入。
- Code Mode 的外层调用源码不等于完整执行轨迹。缺少嵌套调用及返回时，不能仅凭源码出现 wait 就判断该调用只在等待。

因此检测规则须区分完整证据、可疑迹象和无法判断，不把事件缺失当作行为未发生。

## 已发现的定义冲突

用户示例中的 planning、code、reread files、subagents、waiting、wasted 尚不能直接构成互斥的饼图分类。

- subagents 描述执行主体；子 Agent 也可以规划、读取或等待。
- planning / code / reread / waiting 描述行为，但一个调用也可能包含多类行为。
- wasted 是对必要性的判断，不能仅凭行为名称确定。

Q5 已确认分开呈现执行主体、行为归因和异常标签，各维度内部去重、跨维度不相加，不能可靠区分时保留混合 / 未知。Q15 进一步确认纯异常调用按调用去重计价，混合调用不按工具数平摊；因此不再把原始示意的六项直接画成互斥饼图。

## 已确认的产品边界

- Q1：首先服务重度使用 Coding Agent 的个人开发者；支持单次任务事后复盘。用户随后明确增加运行中会话的实时数据分析展示，两者都在 MVP 范围内。
- Q2：以疑似可优化费用、触发证据和置信度呈现判断；重复行为不直接等同于浪费，不承诺可疑金额必然能够省下。
- Q3：MVP 全部本地处理原始日志，不上传源码、提示词或工具输出；后续分享能力另定脱敏规则。
- Q4：一个主会话及明确归属的子会话作为分析单元，恢复会话继续累计，不自动按对话内容拆分任务。
- Q5：执行主体、行为归因、异常标签分开呈现；各维度内部去重，跨维度不相加；证据不足保留混合 / 未知。
- Q6：以日志写出新用量后 5 秒内更新界面为目标，显示最近数据时间；未上报用量标为待更新，不按运行时长估造 Token。
- Q7：Token 分项报告，credits / 货币金额标注估算依据；缺字段或费率显示未知 / 不完整，不填零，不以部分小计冒充总额。
- Q8：不另存会话内容和历史分析结果，只保留费率、规则等偏好；再次查看时重读来源日志。
- Q9：主动启动本地只读采集服务，浏览器展示，保留历史导入；只读选择的日志目录，不自启动，不修改或终止 Agent。
- Q10：独立模型调用为逐轮明细单位，再按用户请求与会话聚合；来源只有汇总时不伪造逐轮数值。
- Q11：同一 Agent 在 5 分钟内至少 3 次读取同文件、同范围、同内容，且符合阶段与证据条件时提示；修改、新指令或压缩恢复后重置计数。
- Q12：同目标连续至少 3 次纯 wait / poll，间隔不超过 60 秒，结果不变且有新增模型用量时提示；不按等待时长推算费用。
- Q13：同一 Agent 在 10 分钟内至少两轮“压缩 → 重读相同内容”时提示，展示证据链；不把没有代码改动视为没有进展。
- Q14：使用离线可用、有来源及适用范围的官方费率快照，允许自定义费率；不能确认适用条件就保留未知，不作统一兑换。
- Q15：只有证据充分且可计价的纯异常调用进入疑似可优化费用；混合调用展示关联费用，首次正常基线不计入，多规则按调用去重。
- Q16：父子成本树区分自身与含子会话合计；缺失日志明示缺口，复制历史不重复计费，真正新增调用的用量照常计入。
- Q17：展示高 / 中 / 低证据置信度，允许本次分析标记必要操作；不改原始用量，优化建议附适用条件并由用户手动执行。
- Q18：htop 式主子会话列表、消耗趋势与异常摘要组成首屏，点击钻取调用时间线、成本树和证据，始终标明最近数据时间与完整性。
- Q19：首发优先验证 macOS 与主流 Chromium 浏览器，同时接入 Codex / Claude Code；只对样本验证过的日志版本承诺完整支持。
- Q20：服务显式启停，关闭网页不自动停止；退出清空临时内容，坏文件隔离提示，日志静默不视为完成，采集操作不终止 Agent。

领域定义见 [CONTEXT.md](../CONTEXT.md)，隐私边界见 [ADR 0001](adr/0001-keep-session-content-on-device.md)，本地采集见 [ADR 0002](adr/0002-use-local-collector-and-dashboard.md)，异常金额归因见 [ADR 0003](adr/0003-account-for-anomalous-model-calls.md)。所有产品问题均已确认，本地实现与验证记录见 `.scratch/coding-agent-cost-monitor/README.md`。

## 第一轮：已确认

### Q1 首要场景

第一个真实用户是谁？第一版必须在什么时刻帮助他完成哪个具体动作？

用户采用默认建议：先服务重度使用 Coding Agent 的个人开发者，完成单次任务的事后复盘，定位最贵行为并调整下一次工作方式。

随后用户新增要求：还要支持实时会话的数据分析展示。这覆盖了原先“仅事后复盘”的范围限制，实时分析与复盘均纳入 MVP；刷新目标在 Q6 决定。用户只请求展示与分析，没有授权自动干预 Coding Agent。

### Q2 “浪费”的证据标准

同一文件读取多次，其中一些发生在修改后验证或上下文恢复时。什么证据足以把某次读取及其相关消耗判定为浪费？

用户采用默认建议：分开呈现已记录用量、行为归因和疑似可优化费用，附触发证据与置信度；没有充分证据时，不把可疑开销宣传成必然可以省下的金额。

### Q3 数据边界

完整会话日志是否允许离开用户设备？

用户采用默认建议：第一版全部本地处理，不上传源代码、提示词或工具输出；分享能力以后另定脱敏规则。

## 第二轮：已确认

实时需求加入后重新梳理了依赖关系。用户以第二次“全采用默认回答”确认本轮 Q4–Q8，不表示同意后续轮次的建议。

### Q4 一次复盘的边界

一次主会话可能包含多个用户请求、暂停恢复及多个子会话。实时展示与事后复盘把什么范围称为“本次任务”？

用户采用默认建议：MVP 将一个主会话及有明确归属证据的子 Agent 会话作为一个分析单元，实时展示与复盘使用同一边界；恢复同一主会话继续累计，不自动按对话内容切分任务，也不自动合并不同主会话。

### Q5 分类维度

一个子 Agent 的调用同时包含读取和等待时，如何避免同一笔用量被重复计算？

用户采用默认建议：分开呈现执行主体、行为归因和异常标签。每个用量视图内部去重，跨视图不相加；行为证据不足时保留“混合 / 未知”，不强凑百分比。具体行为集合和多异常汇总算法留待后续确认。

### Q6 实时性目标

用户所说的“实时”要求新用量多久反映到界面？模型正在运行但还未写出用量时，界面如何表示？

用户采用默认建议：以来源日志写出用量后 5 秒内更新界面为目标，显示最近一次数据时间；尚未得到新用量时标注待更新，不按运行时长猜测 Token。这是目标而非已通过验证的性能承诺，后台运行和支持平台的范围需随接入方案确定。

### Q7 不完整日志与费用估算

如果日志缺少最终输出用量、模型费率或实际扣费，dashboard 允许显示什么结论？

用户采用默认建议：Token 按可验证的日志字段分项报告；credits / 货币金额只在依据充分时展示并标明估算。缺失字段或费率显示“未知 / 数据不完整”，不当成零，不以已知部分小计冒充完整总额，也不把 API 等值估算说成订阅实际扣款。具体费率来源和版本留待后续确认。

### Q8 历史副本

是否允许分析器在来源日志之外，默认另存可恢复的会话内容或历史分析数据？

用户采用默认建议：首版只在本次使用期间保留读取的内容和分析结果，不另存历史副本；可以保存计费与检测偏好。再次查看历史时重新读取来源日志。

## 第三轮：已确认

用户以第三次“全部采用默认回答”确认 Q9–Q14。以下阈值是 MVP 的初始规则，尚未通过实际样本验证，不是普遍成立的浪费判据。

### Q9 接入与持续采集方式

为了持续更新本机日志，用户可接受怎样的启动与接入过程？

用户采用默认建议：用户主动启动一个本地只读采集服务，通过浏览器使用 dashboard；服务仅向本机开放，读取用户明确选择的日志目录，并保留历史文件导入。第一版不自启动、不扫描未选择的目录、不改 Agent 配置、不自动暂停或终止 Agent。首发平台与进程生命周期在接入选择确认后细化。

### Q10 “每轮”的单位

一个用户请求触发多次模型请求 / 响应循环时，逐轮明细应该按什么单位展示？

用户采用默认建议：以可辨识的独立模型调用为最小明细，再按用户请求、会话和分析单元聚合。一次用户请求不能冒充一次模型调用；来源只能提供汇总时保留汇总，不人为拆成看似精确的逐轮费用。

### Q11 重复读取规则

哪些重复读取值得提示，哪些属于上下文恢复或验证？

用户采用默认建议：同一 Agent 在同一上下文阶段，5 分钟内对同一文件相同范围、相同内容读取至少 3 次时触发提示；已观测修改、新用户指令或压缩恢复会重置该阶段的重复计数。压缩后的首次恢复读取不单独算异常。缺少可比较内容 / 范围时只能提示低置信度迹象，不宣称已经验证内容重复。没有观察到修改，不意味着已证明文件未变化。

### Q12 wait / poll 空转规则

怎样区分必要等待与反复花费模型用量查询不变状态？

用户采用默认建议：同一主体针对同一目标连续至少 3 次纯 wait / poll，查询间隔均不超过 60 秒，且返回无新输出 / 状态变化，并存在对应新增模型用量时触发提示。单次长等待不触发；得到新结果或状态变化会打断连续计数。等待时间本身不换算成 Token 或费用；缺少返回状态或嵌套执行证据时不宣称已证实纯等待。

### Q13 上下文压缩循环规则

什么样的压缩与重读序列应该提示为疑似循环？

用户采用默认建议：同一 Agent 在 10 分钟内出现至少两轮“压缩 → 重读相同内容”的可验证链时提示，展示压缩边界与重读证据。单次压缩不触发，不能仅因没有改代码就认定没有进展；正常恢复和只读任务仍可能产生类似序列，因此提示不等于证实浪费。该检测跨上下文阶段观察，不受 Q11 的阶段计数重置影响。

### Q14 费率依据

模型与价格会变化，分析历史会话时应该依据什么费率？

用户采用默认建议：提供可离线使用的官方费率快照，记录来源、核对日期及已知适用范围；允许用户明确提供自定义费率并标注其来源。无法确认模型、速度 / 上下文计费条件或历史适用范围时显示未知 / 不完整，不直接套用今天的价格，不采用统一 Token → credits → 美元换算系数。

## 第四轮：已确认

用户以第四次“全部默认建议”确认 Q15–Q20。

### Q15 工具归因与异常金额

一次模型调用同时包含有效工作与可疑读取时，如何避免把整轮费用错误地归给一个工具？

用户采用默认建议：只有符合完整异常规则、可观察行为均属于异常且用量可计价的模型调用，进入“疑似可优化费用”汇总。混合调用只显示“关联调用费用，无法精确拆分”，不进入该汇总，也不按工具次数均摊。

同一调用触发多个异常时按调用去重；对重复读取或轮询序列保留首次正常读取 / 查询为基线，达到触发阈值后，只把基线之后符合规则的重复调用纳入候选。价格缺失或计量范围无法确认时仍保留异常证据，但金额标为未知 / 不完整。该数值始终是异常相关费用估算，不是保证能够省下的金额。

### Q16 父子范围与数据缺失

只拿到主会话日志、部分子会话缺失时，成本树和总费用应该怎么呈现？

用户采用默认建议：明确区分“自身用量 / 费用”和“含子会话合计”，不把两者相加；缺失子日志时标出缺口与已知范围，不越过用户选择的目录自动寻找。若来源确有覆盖整棵树的可靠汇总，可保留该汇总，但不能据此虚构子会话明细；只有部分资料时显示已知小计，不冒充完整总额。

复制的历史用量记录、重复消息和未变化累计快照不算新消耗；新模型调用真正再次计入的输入 / 缓存用量仍须计入，不能因为内容相同就删除。无法证明归属的会话不硬挂到成本树。已发现的子会话数量不宣称等于实际全部子会话数量。

### Q17 证据等级、误报与建议

用户如何理解不确定性，并纠正必要操作被标为异常的情况？

用户采用默认建议：使用高 / 中 / 低证据置信度，不提供未经校准的百分比。每项异常展示命中规则、对应调用和缺少的证据；高置信度表示异常模式有完整证据，不表示必然没有必要。

允许用户将某项标记为“必要操作”，仅影响本次分析的异常提示与候选费用，不改原始用量，也不持久保存该判断。优化建议采用可解释的规则模板，附适用前提；区分用户可调整的工作方式与需要 Agent 提供方修复的行为，不承诺不存在的开关，不自动改配置或发送指令。

### Q18 dashboard 的首屏与钻取路径

用户进入 dashboard 后，首先需要看懂什么，如何进一步核查？

用户采用默认建议：首屏围绕“哪个会话正在产生新记录、消耗增长多快、哪里值得检查”，采用 htop 式可展开主子会话列表，配用量 / 费用趋势与异常摘要。允许按用量、可计价费用和基于已上报用量的增速排序；最后数据时间与计量完整性始终可见。

点击分析单元进入模型调用时间线、父子成本树和异常证据；历史复盘复用同一统计口径。执行主体、行为归因和异常标签保持分层，不混成一张互斥饼图；演示数据与真实来源明确区分，不合并汇总。

### Q19 首发运行环境与格式覆盖

第一版要承诺支持到哪些环境和日志版本？

用户采用默认建议：优先在用户当前的 macOS 环境及主流 Chromium 浏览器验证本地运行，Codex 与 Claude Code 都提供接入。完整支持只声明已通过样本验证的日志版本；未知格式明确标记部分解析或不支持，不能静默计为零。其他操作系统不作首发支持承诺。

确认产品支持范围不等于授权代理现在扫描个人日志。实现验证优先使用公开或合成样本；需要私人真实样本时另行取得具体文件范围的授权。

### Q20 采集生命周期与故障表现

关闭网页、停止采集或某个日志损坏时，用户应该看到什么？

用户采用默认建议：采集服务由用户显式启动 / 停止，界面说明关闭网页不自动停止服务。停止采集后可以继续查看本次结果，退出服务后清空临时内容；这些动作都不停止 Coding Agent。

单个文件损坏、权限不足、截断或轮转不应拖垮其他来源；受影响来源明确提示异常和数据不完整，未写完的最后一行等待补齐，不伪造零消耗。恢复采集或重新读取不能重复计费。日志静默只显示暂无新记录，不据此认定 Agent 已完成；采集连接状态与来源数据新鲜度分别展示。
